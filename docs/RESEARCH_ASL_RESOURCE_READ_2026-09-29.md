## Observed implementation

In the inspected ASL image, LoadResource(short, ...) at 0x24b44 formats the ID
as text and dispatches the string-name overload. The latter uses virtual
resource-finder calls. The inspected non-localized finder at 0x28ce8 opens
bundle resource files, selects the base resource map, parses the numeric ID,
calls Get1Resource, copies its bytes, restores the resource-file selection and
closes the map. These are static observations, not proof of the concrete
receiver, branch or results in AE's earlier late scan.

## Public-API standalone comparison

New `read_bundle_pipl.cpp` uses CoreFoundation/Carbon APIs in its own process,
not ASL private calls. It reads the base PiPL resource ID 16000, hashes bytes,
and checks CFBundleIsExecutableLoaded before/after. No CFBundleLoadExecutable
or plugin entrypoint is called. This checks a comparable public resource-read
path, NOT full ASL or host-state equivalence.

## Decision

Do not change RSMB or production loader based on these results. In-host resource
state/dispatch, PiPL interpretation and later registry insertion remain distinct
unknowns. Historical PiPL-only and RSMB late registration remain FAIL.

Next safe discriminator: prepare an owned fixture variant with a standalone
.PiPL resource containing identical property bytes, keeping the same native
lifecycle and a fresh match identity. First verify package/signature/resource
bytes offline, then predeclare a separate controlled late-registry gate. This
would test resource representation without guessing private lifecycle calls.
New variant build and live gate: NOT RUN in this iteration.
